# V275: Set-indexed in-flight page-walk join, sole active kernel

**Evidence class E1 only**: Python training model and exploratory RTL; no RTL simulation, mapped synthesis, STA, max-cap/slew or physical power. No integrated tile change, no performance or novelty claim. V274 is retired.

1. **Bottleneck law.** With four outstanding translation slots, walk latency L, arrival rate lambda and same-page merge fraction h, walker admission demand is approximately lambda_walk=lambda*(1-h). A 2-set/2-way join is unsaturated only if per-set walk demand lambda_s<2/L, while a fully associative four-slot join can use pooled 4/L. Bursty arrivals and retire bubbles tighten both bounds; this relation is a testable first-order model, not a fitted result.
2. **Mechanism.** Hash page-walk key (VPN+ASID+mode+generation) into two sets, compare at most two in-flight tags, merge same-page requests into a bounded waiter counter, and launch a walk only on a miss with a free set way. A returned walk releases its entry and broadcasts to waiters. This is a conventional set-associative design trade-off, NOT a novelty assertion.
3. **Strongest equal-resource baseline.** Four-slot fully associative join, identical tag width, waiter bits, walk/retire ports, same scoreboard, same admission policy and identical walker bandwidth. Also compare a fully associative prefix-gated comparator that uses the hash to suppress full-tag switching. No extra entries, ports or buffering allowed for the candidate.
4. **Predicted win/loss boundary.** Low occupancy, high page reuse and balanced set pressure should preserve accepted throughput while the indexed candidate activates only two full-tag comparisons rather than four. Hot-set collisions or walker saturation should favor the associative control. Physical benefit exists only if comparator/wire savings exceed set decoding and control overhead after equalized wiring.
5. **Smallest RTL.** `tlb_join.sv`, 4 entries, two 2-way sets (`INDEXED=1`) versus a 4-way associative control (`INDEXED=0`). It is exploratory and not yet RTL simulated. Hash is the low key bit solely for controlled sweeps; no security/performance guarantee.
6. **Physical proxy.** Run self-checking RTL simulation; Yosys generic synthesis; Nangate45 mapping and OpenSTA max-cap/slew with explicit 0.5x/1x/2x wire/load; compare area, critical path and gate toggles including prefix-gated control. Unmapped comparator counts are NOT energy.
7. **Workload metric.** Accepted requests/cycle, page walks launched, merged waiters, queue backlog, set conflicts, full-key comparator activations. Include compute-bound (few TLB misses), memory-bound (high misses), divergent (hot-set skew), plus balanced and high-reuse traces.
8. **Decisive falsification.** Any incorrect page-key merge, dropped waiter, nonmatching ASID/mode, lost response, same-or-worse physical PPA versus optimized equal-resource control, or loss of throughput under frozen positive workload retires kernel. First fix once; no more than two physical/plumbing runs.
9. **Unseen prediction.** Freeze holdouts before any RTL/STA evaluation. Positive: 0.20 requests/cycle, 85% reuse across four balanced hot keys; predict accepted-throughput ratio >=0.99 and <=0.6 candidate/full-CAM raw comparator activations (not energy). Negative: 0.40 requests/cycle, all keys in one hash set, predict indexed accepted throughput <=0.8x associative. Tolerances 1% throughput, 10% comparator activity. Do not open until functional RTL and synthesis gates.
10. **Architecture consequence.** If physical gain survives the prefix-gated equal-resource control and holdouts, incorporate the two-set walk-join as a candidate Vektor MMU return-side microblock. Otherwise retain a conventional fully associative coalescer and no tile change.

**Prior art audit (preliminary):** gem5 AMD GPU TLBCoalescer already merges same-virtual-page translation requests and returns to all waiting translations: https://gem5.googlesource.com/public/gem5/+/1d03f6de941520860c673b5f7954c82a46e8b191/src/arch/amdgpu/common/tlb_coalescer.cc . Power et al., HPCA 2014, 'Supporting x86-64 address translation for 100s of GPU lanes' describes a GPU TLB hierarchy with multithreaded page walker and walk cache: https://arch.cs.ucdavis.edu/gpu/memory/2014/02/15/gpummu.html . These establish strong novelty risk; set associativity itself is also standard. This kernel seeks a **measured physical trade-off boundary**, not an original coalescing concept.
